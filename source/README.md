# Hotel Kiosk — документация

> **v5 — MONE UI.** Фронтенд заменён на дизайн-систему MONE из «доп материалов»
> (`wwwroot/kiosk.html`; прежний интерфейс `kiosk-legacy.html` удалён как мёртвый).
> Протокол моста — версионный конверт `{type:"request",version:1,action,...}`;
> C#-адаптер — `KioskActionAdapter` (Application), ответы доставляются в
> `window.KioskBridge.receive`.
> Действия: `system.preflight`, `booking.search`, **`booking.arrivals`**,
> `scanner.scan`, `pms.guest.upsert`, `pms.checkin`, `vision.prepare`,
> `card.detect|read|write|verify|awaitRemoval`, `pms.finalize`, `recovery.inspect`
> **+ возвращённые `payment.create|status|cancel`** (шаг «Оплата» встроен между
> документами и ключами, 7 шагов прогресса).
> Демо без бэкенда: `kiosk.html?demo=1` (бронь MN-48291 / Иванов).
> **Актуальное описание протокола — [`BridgeApi.md`](BridgeApi.md).** Раздел
> «Протокол» ниже сохранён как история: он описывает первую версию моста
> (`KioskBridgeHandler`), которой в сборке больше нет.

## booking.arrivals — «сегодня заезжают»

Гость приходит без кода брони (потерял, забыл) и ищет себя по фамилии.

| | |
|---|---|
| **Запрос** | `{action:"booking.arrivals", payload:{date:"2026-08-20"}}` — `date` необязателен, по умолчанию сегодня |
| **Ответ** | `{date, count, arrivals:[{genericNo, lastName, firstName, arrivalDate, departureDate, stayAmount, balance}]}` |
| **Ошибки** | `PMS_OFFLINE` — PMS не поддерживает список или не отвечает; `BOOKING_DATES_INVALID` — не разобрана дата |

Кнопка «Сегодня заезжают» на экране поиска показывается **только** если PMS умеет эту
операцию: `system.preflight` возвращает `pms.missing`, где «список заездов» означает
«операции нет». Для универсальной PMS это определяется тем, описан ли `Pms:Generic:Arrivals.Path`.

Выбор записи подставляет код брони и фамилию в форму и сразу запускает `booking.search` —
дальше флоу обычный.

## Протокол

### Запрос из JS → C#

```json
{
  "id": 1,
  "type": "findReservation",
  "payload": { "bookingCode": "BR-001", "lastName": "Иванов" }
}
```

### Ответ C# → JS

```json
{
  "id": 1,
  "result": { "found": true, "guest": { "firstName": "Иван", "lastName": "Иванов" } },
  "error": null
}
```

### Push-события (C# → JS без запроса)

```json
{
  "type": "paymentConfirmed",
  "payload": { "orderId": "TX-123", "rrn": "RRN-456" }
}
```

## Методы

### 1. `findReservation`

Поиск брони по номеру + фамилии. Вызывает `Logus /api/SelfCheckin/Authenticate`.

**Payload:**
```json
{
  "bookingCode": "string",
  "lastName": "string"
}
```

**Result (успех):**
```json
{
  "found": true,
  "guest": {
    "firstName": "Иван",
    "lastName": "Иванов"
  },
  "reservation": {
    "id": "BR-001",
    "roomCode": "305",
    "roomTypeName": "Стандарт",
    "price": 5000,
    "arrivalDate": "2026-07-25T14:00:00",
    "departureDate": "2026-07-28T12:00:00"
  }
}
```

**Result (не найдена):**
```json
{ "found": false }
```

---

### 2. `scanPassport`

Сканирование паспорта через Regula SDK.

**Payload:** `{}` (пустой)

**Result (успех):**
```json
{
  "success": true,
  "passportNumber": "4500 123456",
  "fullName": "ИВАНОВ ИВАН ИВАНОВИЧ"
}
```

**Result (ошибка):**
```json
{
  "success": false,
  "error": "Сбой сканера: scanner offline"
}
```

---

### 3. `processPayment`

Создание QR-заказа на оплату в AlfaBank. Запускает фоновый опрос статуса.

**Payload:**
```json
{
  "amount": 5000
}
```
> `amount` опционален — если не передан, используется цена из брони.

**Result (успех):**
```json
{
  "qrImageBase64": "PHN2Zw...",
  "qrPayload": "https://pay.alfa-bank.ru/order/...",
  "orderId": "TX-123"
}
```

**Result (ошибка):**
```json
{ "error": "Оплата отклонена: insufficient funds" }
```

**Push-события (после ответа):**

| Тип | Payload | Описание |
|-----|---------|----------|
| `paymentConfirmed` | `{ "orderId", "rrn" }` | Оплата подтверждена |
| `paymentFailed` | `{ "orderId", "reason" }` | Оплата не прошла (`timeout` / текст ошибки) |

---

### 4. `checkPaymentStatus`

Ручная проверка статуса оплаты по orderId.

**Payload:**
```json
{
  "orderId": "TX-123"
}
```

**Result:**
```json
{ "confirmed": true }
```
или
```json
{ "confirmed": false }
```

---

### 5. `writeKeys`

Четыре шага, строго по порядку:
1. **Проверка брони** — `findReservation` должен был пройти в этой сессии (иначе отказ).
2. **Проверка оплаты** — киоск сам запрашивает статус заказа у банка (`sbp_c2b/status.do`, `DEPOSITED`); без подтверждённой оплаты ключ не пишется и заселение не проводится. При сумме брони 0 оплата не требуется.
3. Фиксация заселения в Logus (`SelfCheckin/CheckIn` WebAPI — только бизнес-статус, ключи он не пишет).
3a. **Паспортные данные гостя → Logus** (если паспорт сканировался и включён `LogusApi:SendGuestDocuments`):
   `GET /api/Reservation/{genericNo}` → Guid брони; `POST /api/GuestProfile` → профиль с документом;
   `POST /api/Reservation/{guid}/UpdateGuests` → привязка к брони. Не блокирует заселение —
   при сбое персоналу уходит Telegram-уведомление «внесите данные вручную».
4. Запись ключ-карты напрямую через REST-сервер VisionLine (`192.168.4.55:27015`, секция `VisionLine` в appsettings).

**Payload:**
```json
{
  "roomCode": "305"
}
```
> `roomCode` опционален — если не передан, используется из предыдущего `findReservation`.

**Result (успех):**
```json
{
  "success": true,
  "cardUid": "VL-777"
}
```
> `cardUid` — реальный идентификатор карты от VisionLine. При сбое записи
> чекпоинт не очищается: Logus-заселение уже прошло, карты нет — персонал
> увидит незавершённую сессию и выдаст карту вручную.

**Result (ошибка):**
```json
{
  "success": false,
  "error": "Logus: Сбой заселения"
}
```

---

### 6. `cancelReservation`

Отмена брони в Logus с указанием причины. Сохраняет причину в `CheckInContext` для компенсации.

**Payload:**
```json
{
  "reservationId": "BR-001",
  "cancelReason": "GuestRequest"
}
```
> `reservationId` опционален — если не передан, используется из предыдущего `findReservation`.
> `cancelReason` опционален — по умолчанию `GuestRequest`.

**Допустимые значения `cancelReason`:**

| Код | Описание |
|-----|----------|
| `GuestRequest` | Гость отказался от заселения |
| `Compensation` | Компенсация (техническая ошибка) |
| `Overbooking` | Нет свободных номеров |
| `SystemError` | Системная ошибка |

**Result (успех):**
```json
{ "success": true }
```

**Result (ошибка):**
```json
{
  "success": false,
  "error": "Logus отклонил отмену: HTTP 400"
}
```

**Побочные эффекты:**
- Останавливает фоновый опрос оплаты (`_pollCts`)
- Сохраняет `CancellationReason` в `CheckInContext` (сессия на диске)
- Очищает сессию после успешной отмены

## Типовые сценарии использования

### Нормальное заселение

```
1. findReservation    → экран подтверждения данных
2. scanPassport       → экран проверки (паспорт + данные брони)
3. processPayment     → экран QR-оплаты
   └─ push: paymentConfirmed → экран записи ключа
4. writeKeys          → экран успеха
```

### Отмена на экране оплаты

```
1. findReservation
2. scanPassport
3. processPayment     → экран QR-оплаты
4. cancelReservation  → возврат к поиску брони
   └─ сохраняет причину в CheckInContext
```

### Компенсация после сбоя

```
1. findReservation
2. scanPassport
3. processPayment     → платёж прошёл
4. writeKeys          → ОШИБКА (Logus CheckIn failed)
   └─ CheckInStateMachine запускает компенсацию:
      - Возврат оплаты (AlfaBank.RefundPaymentAsync)
      - Отмена брони (Logus.CancelReservationAsync с сохранённой причиной)
```

## Конфигурация

Все настройки хранятся в `appsettings.json` (копируется в выходную папку при сборке).

### Проверка конфигурации при старте

Киоск проверяет конфигурацию **до** открытия окна гостя (`KioskConfigurationValidator`) и, если
найдены проблемы, показывает оператору один диалог со списком — сначала блокеры, затем
предупреждения. Каждая позиция содержит ключ в нотации `appsettings.json` и объяснение,
что именно не будет работать.

Это сделано потому, что незаполненные ключи раньше приводили к тихому отказу в середине флоу:
гость уже стоял перед экраном, когда выяснялось, что паспорт нечем сканировать, а QR нечем
оплатить.

| Ключ | Severity | Что не работает при пустом значении |
|------|----------|-------------------------------------|
| `LogusApi:BaseUrl` | Error | Подставился бы дефолт — облако `api-hms.logus.pro` вместо PMS отеля |
| `LogusApi:Login` / `Password` | Error | Поиск брони и заселение |
| `Regula:AgentScanPath` | Error | Только при `CaptureSource=reader`: путь агента захвата кадра со считывателя |
| `AlfaBankQr:Login` / `Password` | Error | Создание QR-заказа (СБП) |
| `AlfaBankQr:PollIntervalSeconds` ≤ 0 | Error | Бесконечный опрос статуса платежа |
| `VisionLine:BaseUrl` | Error | Запись ключ-карты |
| `Telegram:BotToken` / `ChatId` при `Enabled=true` | Error | Стойка не узнает о незаписанной карте и сбое заселения |
| `CardTerminal:BaseUrl` (некорректный URL) | Error | Оплата картой при включённом `CardTerminal:Enabled` |
| `LogusApi:PaymentTransactionCode` | Warning | Оплата не попадёт на folio брони, потребуется ручная сверка |
| `VisionLine:Token` | Warning | Мост используется без авторизации |
| `AlfaBankQr:TestMode = true` | Warning | Включён тестовый контур эквайринга |
| `CardTerminal:Enabled = false` | Warning | Оплата только по QR |

В демо-режиме (`HotelKiosk.UI.exe --demo`) проверка пропускается — бэкенд не нужен.
Полный список правил: `src/HotelKiosk.Infrastructure/Configuration/KioskConfigurationValidator.cs`.

### Секреты

Пароли и токены **не хранятся** в отслеживаемых файлах: `appsettings.json` и `appsettings.*.json`
перечислены в `.gitignore`. Заполняйте их локально на киоске (шаблон — `appsettings.example.json`)
либо через `appsettings.local.json` / переменные окружения. Пустые значения — не ошибка сборки:
приложение запустится и покажет список незаполненных ключей.

### Serilog

Секция `Serilog` в `appsettings.json` — рабочая (раньше путь и уровень были захардкожены в коде).
Если секции нет или она не разбирается, используются прежние значения: `Information`,
`logs/kiosk-.log` с суточной ротацией и консоль.

Две особенности, из-за которых секцию пришлось разбирать вручную:

- **`ReadFrom.Configuration` здесь не работает.** Он ищет синки через
  `DependencyContext` и в данном окружении не находит ни одного: секция читается
  без ошибки, а лог не появляется — и даже неизвестное имя синка не бросает
  исключение. Поэтому `KioskLogging` разбирает секцию явно и сообщает об опечатках
  через `SelfLog`.
- **Относительный путь привязывается к папке приложения**, а не к рабочему
  каталогу: при автозапуске киоска рабочая папка не гарантирована, и лог
  оказывался в произвольном месте (чаще всего — нигде). Путь указывайте
  относительным (`logs/kiosk-.log`) либо абсолютным.

Опечатка в имени синка теперь видна в логе, а не приводит к молчаливому
отсутствию журнала.

### Pms — выбор PMS

Киоск работает с PMS через порт `IPmsProvider` и ничего не знает о конкретной
системе. Выбор делается одним ключом:

```json
"Pms": { "Provider": "logus", "DisplayName": "Logus" }
```

| `Pms:Provider` | Адаптер | Когда применять |
|----------------|---------|-----------------|
| `logus` (по умолчанию) | `LogusApiService` | Боевой контур Logus — контракт сверен с живым API |
| `generic` | `GenericPmsService` | Любая PMS с REST/JSON-контрактом: Shelter, 1С:Отель, WinHotel, «Проф-Отель», Hoteltron |

`DisplayName` — имя для интерфейса и логов. Не задан — берётся `Pms:Generic:Vendor`.

Неизвестный код PMS блокирует старт: молчаливый откат на Logus выглядел бы
как «бронь не найдена» без всякой причины.

### Универсальный PMS-адаптер (Pms:Generic)

Всё, что различается между PMS — URL, имена полей, способ авторизации, формат
дат и сумм — описывается в конфиге. Киоск не знает ни про `data.reservation.id`,
ни про `reservations/search`; он знает про `SelfCheckinInfo` и `Path = ...`.

| Параметр | Описание | Пример |
|----------|----------|--------|
| `Vendor` | Код PMS для логов и сообщений | `shelter` |
| `BaseUrl` | Адрес WebAPI | `https://pms.example.ru/api/v2` |
| `AuthMode` | `none` \| `basic` \| `bearer` \| `token-header` \| `token-query` | `basic` |
| `Login` / `Password` | Для `basic` | `KIOSK_USER` / `***` |
| `Token` / `TokenHeaderName` / `TokenQueryName` / `TokenPrefix` | Для остальных режимов | `***` / `X-Api-Key` / `token` / `Bearer ` |
| `TimeoutSeconds` | Таймаут запроса | `20` |
| `DefaultHeaders` | Заголовки ко всем запросам | `{"X-Hotel-Id":"1"}` |
| `ErrorInBody` | Ошибка приходит кодом в теле, а не HTTP-кодом | `true` |
| `SuccessPath` | Поле-признак успеха в теле | `success` |
| `ErrorMessagePath` | Поле с текстом ошибки | `error.message` |
| `SendGuestDocuments` | Передавать паспортные данные | `false` |
| `PaymentTransactionCode` | Код транзакции; **пусто = оплата не попадёт на счёт брони** | `CASHLESS` |
| `CancellationReasonCodes` | Наши коды → коды PMS | `{"GuestRequest":"GUEST_REQUEST"}` |

**Операции** (`Authenticate`, `CheckIn`, `Cancel`, `AddPayment`, `Arrivals`,
`ReservationDetails`, `UpsertGuest`, `AttachGuest`, `Ping`) описываются одинаково:

```json
"CheckIn": {
  "Enabled": true,
  "Method": "POST",
  "Path": "reservations/@{reservationId}/checkin",
  "Body": { "roomNumber": "@{roomNo}" },
  "Headers": { "Idempotency-Key": "@{reservationId}" },
  "Paths": { }
}
```

- `Path` относительно `BaseUrl`, поддерживает плейсхолдеры, значения URL-экранируются
- `Body` — значения вида `@{...}` подставляются; **тип задаёт формат**: `@{amount:0.00}` даёт
  число `5000.00` (точка, не запятая), а `@{roomNo}` — строку `"305"` (номер комнаты
  приводить к числу нельзя)
- `Paths` — точечные пути в ответе: `"data.reservation.room.number"`, регистр не важен

Плейсхолдеры операций: `reservationNo`, `reservationId`, `reservationGuid`, `key`,
`confirmationMode`, `roomNo`, `cancellationReason`, `amount`, `transactionId`,
`uniqueId`, `transactionCode`, `date`, `propertyId`, `personId`, `profileGuid`,
`lastName`, `firstName`, `middleName`, `birthDate`, `documentNumber`, `documentSeries`.

**Что можно не описывать.** Операция без `Path` считается неподдерживаемой: киоск
скажет «PMS не поддерживает», а не получит 404. Так отключаются, например, список
заездов (кнопка «Сегодня заезжают» не показывается) и паспортные данные
(заселение продолжит работать, персонал внесёт данные вручную).

Обязательны только `Authenticate` и `CheckIn` — без них заселение невозможно,
и валидатор покажет это как блокер при старте.

`system.preflight` возвращает `pms.vendor` и список `pms.missing` — персонал
видит, чего подключённая PMS не умеет, до первого гостя.

**Честное ограничение.** Адаптер покрывает PMS с REST/JSON. Системы с SOAP
(1С:Отель в части старых конфигураций) требуют отдельного адаптера — но карта
операций и путей полей остаётся той же, то есть конфиг переиспользуется.

Образец с комментариями: `pms-generic.sample.json` в корне репозитория.
Это **иллюстрация формата, а не боевой конфиг** — URL и имена полей берутся
из документации вашей PMS.

**Паспортные данные.** Если у PMS нет эндпоинтов профиля гостя
(`SendGuestDocuments=false` или операция не описана), киоск не пытается их
отправить: заселение продолжается, персонал получает уведомление «внесите
данные вручную». Так же ведёт себя `system.preflight` — операция отсутствует
в `pms.missing`.

### Диагностика киоска (--selftest)

Проверяет все интеграции и печатает отчёт, который можно унести на стойку:

```
publish\HotelKiosk.UI.exe --selftest
publish\HotelKiosk.UI.exe --selftest C:\temp\отчёт.txt
```

Диалог конфигурации при этом не показывается, окно гостя не открывается.
Отчёт по умолчанию сохраняется рядом с приложением как `selftest-ГГГГММДД-ЧЧММСС.txt`.

```
--- PMS: Shelter ---
Адаптер: generic
SHELTER: не поддерживается — список заездов, передача паспортных данных
Не поддерживается (заселение продолжит работать): список заездов, передача паспортных данных
  Живость PMS                      ОК (12 мс)

  Описанный контракт (сверьте с документацией вашей PMS):
    Адрес:   https://pms.example.ru/api/v2
    Авторизация: basic
    Поиск брони        POST reservations/search
    Заселение          POST reservations/@{reservationId}/checkin
    Заезды на дату     НЕ ОПИСАНА — будет отключена
    ...

    Пути в ответе (пусто = поле не читается):
      data.reservation.id             номер брони
      —                               guid брони
```

Для универсальной PMS отчёт печатает **всё, что описано в конфиге** — URL, методы и пути в
ответе. Это то, что сверяют с документацией PMS: опечатка в пути или URL видна сразу,
а не как «бронь не найдена» при живом госте.

Проверки живости ограничены 15 секундами: висящий сетевой хост не превращает
диагностику в зависание.

### LogusApi

| Параметр | Описание | Пример |

#### Тайминги оплаты

Значения собираются в единственном типе `PaymentPollingPolicy`
(`src/HotelKiosk.Application/Services/PaymentPollingPolicy.cs`) и раздаются всем потребителям:

| Параметр | Что задаёт | Источник |
|----------|-----------|----------|
| `PaymentPollIntervalSeconds` | Интервал опроса статуса QR-заказа | `AlfaBankQr:PollIntervalSeconds`, при отсутствии — `CheckInStateMachine:PaymentPollIntervalSeconds` |
| `CardPollIntervalSeconds` | Интервал опроса статуса карточной операции | `CardTerminal:PollIntervalSeconds`, при отсутствии — QR-интервал |
| `DeadlineMinutes` | Сколько ждать подтверждения, потом отменить QR-заказ | `AlfaBankQr:QrLifetimeMinutes`, при отсутствии — `CheckInStateMachine:PaymentCheckTimeoutSeconds / 60` |

Значения с клампингом снизу в 1: нулевой интервал дал бы бесконечный цикл опроса.

`PAY_POLL_MS` / `PAY_DEADLINE_MS` и не может разойтись с бэкендом. Открытая напрямую
в браузере страница (без хоста киоска) использует прежние значения 3 с / 5 мин.

### CardTerminal — оплата картой через пинпад

Гость выбирает способ на отдельном экране: QR СБП или карта. Доступность
карты киоск проверяет health-check'ом агента терминала (`getPaymentMethods`).

Подключение любого банка делается через **локальный агент пинпада** на
киоск-ПК — тонкий HTTP-сервис, оборачивающий софт терминала. Контракт агента:

| Метод | Запрос | Ответ |
|-------|--------|-------|
| `POST {ChargePath}` | `{"orderId":"...","amount":5000.00}` (рубли) | `{"status":"CONFIRMED\|PENDING\|DECLINED","transactionId":"...","rrn":"...","error":"..."}` |
| `GET {StatusPath}?orderId=...` | — | та же форма ответа |
| `POST {RefundPath}` | `{"transactionId":"...","amount":5000.00}` | HTTP 200 = возврат принят |
| `GET {HealthPath}` | — | HTTP 200 = агент и терминал живы |

`PENDING` → киоск опрашивает статус раз в `PollIntervalSeconds`; синхронный
`CONFIRMED` в charge-ответе сразу ведёт гостя дальше.

| Параметр | Описание | Пример |
|----------|----------|--------|
| `Enabled` | Оплата картой включена (false — кнопка гаснет) | `false` |
| `BaseUrl` | Адрес агента пинпада на киоск-ПК | `http://localhost:8090` |
| `ChargePath` / `StatusPath` / `RefundPath` / `HealthPath` | Пути эндпоинтов агента | см. контракт выше |
| `TimeoutSeconds` | Таймаут HTTP (списание долгое — гость вводит PIN) | `90` |
| `PollIntervalSeconds` | Интервал опроса PENDING-операции | `3` |

> Секция `CardTerminal` биндится в DI (`services.Configure<CardTerminalOptions>`).
> Раньше этот вызов отсутствовал, адаптер получал пустые дефолты класса, и весь блок
> оплаты картой нельзя было включить правкой конфига.

### VisionLine

Сервер **192.168.4.55**. Реальная схема портов ASSA ABLOY VisionLine
(подтверждено документацией интеграторов):

| Порт | Назначение |
|------|-----------|
| **4000** (TCP) | **PMS-порт** сервера VisionLine — его слушает локальный клиент Logus на стойке для записи ключей энкодером. Протокол закрытый, из интеграционного пакета ASSA ABLOY |
| 27015 (TCP) | Lock Service — порт клиентских приложений работы с замками/картами |

Киоск не может говорить с закрытым PMS-протоколом напрямую. Варианты:

1. **Локальный мост на киоск-ПК** (текущий контракт ниже): небольшой HTTP-сервис,
   внутри которого работает клиент VisionLine (модуль Logus Keylock или наш
   агент с SDK от ASSA ABLOY). Киоск зовёт его по HTTP — конфиг ниже.
   Какой процесс Logus является этим клиентом — показывает
   `scripts/find-visionline-client.ps1` (запустить на стойке во время записи карты).
2. **Запросить у дилера ASSA ABLOY спецификацию внешнего интерфейса**
   («Visionline External/PMS Interface») — тогда напишем прямого TCP-клиента на 4000.
3. Персонал выдаёт карту вручную при сбое — уже реализовано как fallback.

| Параметр | Описание | Пример |
|----------|----------|--------|
| `BaseUrl` | Адрес локального HTTP-моста к VisionLine | `http://localhost:27015` или адрес моста |
| `Token` | Bearer-токен, если мост требует авторизацию. Пусто — запрос уходит без заголовка `Authorization`, и `issuerId` уходит как `null` | `` (пусто = без авторизации) |
| `IssuerId` | Идентификатор источника ключей (если используется) | `` |
| `IssueKeyCardPath` | Путь записи карты | `/IssueKeyCard` |
| `ReadKeyCardPath` | Путь чтения карты | `/ReadKeyCard` |
| `HealthPath` | Путь health-check | `/health` |
| `TimeoutSeconds` | Таймаут запроса (сек) | `20` |
| `HealthMonitorEnabled` | Фоновый монитор живости + автоперезапуск энкодера | `false` |

### Сканирование паспорта: фронтальная камера

Киоск снимает **гостя с открытым паспортом в руках** фронтальной камерой и отправляет кадр
в тот же Regula Document Reader (`POST /process`) для OCR. Физический считыватель не нужен.

Цепочка: `kiosk.html` (`getUserMedia` → canvas → JPEG base64) → `scanner.scan` с
`payload.image` → `IRegulaService.RecognizeFromPhotoAsync` → Regula `/process` → тот же
разбор TEXT-контейнера, что и для считывателя.

| Параметр | Описание | Пример |
|----------|----------|--------|
| `CaptureSource` | `camera` — фронтальная камера, `reader` — считыватель. Пусто = авто: считыватель, если задан `AgentScanPath`, иначе камера | `camera` |
| `CameraWidth` / `CameraHeight` | Размер кадра для OCR. Слишком большой кадр заметно замедляет распознавание | `1280` / `960` |
| `CameraJpegQuality` | Качество JPEG, 0.1–1.0. Ниже 0.6 MRZ читается нестабильно | `0.9` |
| `CameraCountdownSeconds` | Обратный отсчёт до съёмки — гость успевает занять позицию | `3` |
| `AgentScanPath` | Нужен **только** для `CaptureSource=reader` | `` |

Разрешение на камеру выдаётся приложением автоматически (`CoreWebView2.PermissionRequested`):
в киоске диалог подтверждения никто не увидит, и WebView2 иначе молча отказывает.

Камера включается только на экране сканирования и выключается при уходе с него — индикатор
камеры на других шагах не горит.

**Проверка кадра перед съёмкой.** Гость не обязан угадывать момент: кадр
оценивается прямо в браузере, и если в нём никого нет, съёмка ждёт позиции
(до 12 с) с подсказкой в рамке — «встаньте в рамку», «не двигайтесь», «слишком
темно». Проверяется яркость (камера не закрыта крышкой), контраст (перед камерой
есть кто-то) и движение между кадрами (гость выбирает позицию). Лицо и паспорт
так не определить — это задача OCR, но пустые и тёмные кадры до него не доходят.

**Тексты ошибок для камеры** отдельные от считывателя: гостю не говорится
«положите документ на считыватель», когда он стоит в рамке. При проблемах с
оборудованием всегда предлагается позвать сотрудника — гость ничего не
починит, а «повторите» привело бы к залипанию на том же экране.

`system.preflight` сообщает `captureSource` и флаги `devices.camera` /
`devices.scanner`: персонал видит проблему с настройкой до того, как гость
встанет в рамку.

Если `payload.image` пуст, `scanner.scan` обращается к считывателю (прежнее поведение),
так что оба режима уживаются.

### Regula — распознавание документов

Интеграция с **Regula Document Reader Web API** (официальная спецификация v8,
по умолчанию `http://localhost:8080`). Киоск отправляет снимок документа в
`POST /api/process` (сценарий из конфига, запрос только текстовых полей) и
разбирает TEXT-контейнер: серия, номер, ФИО по частям, пол, даты рождения и
выдачи, код подразделения, кем выдан, место рождения. Всё это уходит в Logus
при заселении.

| Параметр | Описание | Пример |
|----------|----------|--------|
| `DocumentReaderUrl` | Базовый URL Web API | `http://localhost:8080/api` |
| `Scenario` | Сценарий обработки Regula | `FullProcess` |
| `ProcessPath` / `HealthPath` | Пути эндпоинтов относительно BaseUrl | `process` / `ping` |
| `AgentScanPath` | Путь локального агента захвата кадра со считывателя (GET → `{"image":"<base64>"}`). Нужен только при `CaptureSource=reader` | `device-scan` |
| `CaptureSource` | `camera` / `reader` / пусто (авто) — см. «Сканирование паспорта: фронтальная камера» | `camera` |
| `CameraWidth` / `CameraHeight` | Размер кадра для OCR | `1280` / `960` |
| `CameraJpegQuality` | Качество JPEG кадра (0.1–1.0) | `0.9` |
| `CameraCountdownSeconds` | Обратный отсчёт до съёмки, сек | `3` |
| `LicenseKey` | Лицензия base64, если передаётся в запросе (иначе лицензия на сервере) | `` |
| `DateFormat` | Формат дат в ответе Regula | `yyyy-MM-dd` |

> Web API работает с готовыми изображениями — за кадром с физического
> считывателя отвечает маленький агент на киоск-ПК (тот же паттерн, что
> агент пинпада): один эндпоинт `GET {AgentScanPath}` → `{"image":"<base64>"}`.
> Если ваш Document Reader сам умеет отдавать снимок по HTTP — укажите его
> путь в `AgentScanPath`.

### Telegram

Уведомления персоналу от киоска (Bot API). Создайте бота через @BotFather,
добавьте его в группу стойки регистрации и узнайте chat_id
(`https://api.telegram.org/bot{token}/getUpdates`).

| Параметр | Описание | Пример |
|----------|----------|--------|
| `Enabled` | Вкл/выкл. Пустой `BotToken`/`ChatId` тоже отключает отправку | `true` |
| `BotToken` | Токен бота от @BotFather. Пусто — уведомления отключены | `123456:AA...` |
| `ChatId` | Chat id группы стойки | `-1001234567890` |

События: ✅ успешное заселение (номер, бронь, UID карты), ⚠️ карта не
записалась (гость заселён, нужна карта вручную), 🛑 Logus не заселил.

> Если `Enabled=true`, а `BotToken` или `ChatId` пусты, отправка не происходит
> **и пишется Warning в лог**. Раньше это уходило в `LogDebug` и полностью
> терялось, то есть стойка просто не узнавала бы о незаписанной карте.
> Валидатор конфигурации покажет эту комбинацию как блокер при старте.

> Формат запроса: `POST {BaseUrl}{IssueKeyCardPath}` с JSON
> `{"room":"305","checkIn":"2026-08-20T14:00:00","checkOut":"2026-08-23T12:00:00"}`.
> Ответ разбирается толерантно: идентификатор карты ищется в полях
> `cardUid` / `uid` / `id`. Если ваш сервер отвечает по другим путям —
> поменяйте `*Path` в конфиге, код пересобирать не нужно.

### Развёртывание

Киоск — это два артефакта, а не один:

| Артефакт | Что это | Куда |
|---|---|---|
| `publish\` | `HotelKiosk.UI` — окно киоска (WPF + WebView2) | киоск-ПК |
| `publish-agent\` | `HotelKiosk.LocalAgent` — служба Windows, health-check Regula раз в 10 секунд | киоск-ПК, если нужен мониторинг |

Сборка одной командой из корня репозитория:

```powershell
.\source\scripts\publish.ps1
```

Скрипт собирает оба проекта. Если в целевом `appsettings.json` уже есть пароли,
публикация **откажется** их затирать шаблоном из репозитория: нужен `-Force`,
тогда рядом останется резервная копия. Только киоск: `-SkipAgent`.

На киоск-ПК требуется:

- Windows 10/11 x64;
- .NET 9 **Desktop** Runtime — публикация framework-dependent;
- WebView2 Runtime — в Windows 11 уже есть, в Windows 10 обычно приезжает с Edge.

Проверка после копирования файлов:

```powershell
publish\HotelKiosk.UI.exe --selftest
```

Отчёт `selftest-<дата>.txt` появится рядом с exe. Три блокера про ключи Logus,
Альфа-Банка и Telegram — это ожидаемо, пока не заполнен `appsettings.json`.

Установка службы агента:

```powershell
sc.exe create HotelKioskLocalAgent binPath= "C:\Kiosk\agent\HotelKiosk.LocalAgent.exe" start= auto
sc.exe start HotelKioskLocalAgent
```

По умолчанию служба работает от `LocalSystem`; папка агента должна быть ей доступна.
Агент не обязателен: Regula киоск проверяет сам перед стартом, агент нужен для
постоянного мониторинга.

Автозапуск киоска — Планировщик заданий, триггер «При входе в систему»:

- программа: `C:\Kiosk\app\HotelKiosk.UI.exe`;
- рабочая папка не важна: `wwwroot` и `logs` берутся от папки приложения, а не
  от текущего каталога;
- **одна и та же учётная запись**: чекпоинт сессии лежит в
  `%LOCALAPPDATA%\HotelKiosk\session.json`, у каждого пользователя Windows он свой;
- второй экземпляр не откроется: киоск держит именованный мьютекс и молча выходит.

Обновление: закрыть киоск, заменить файлы, сохранить `appsettings.json`, запустить.
Скрипт публикации предупредит, если конфиг вот-вот будет затёрт.

### Запуск

1. Скопируйте `appsettings.json` из `src/HotelKiosk.UI/` в папку с приложением
   (или возьмите `appsettings.example.json` как шаблон)
2. Заполните `LogusApi:Login` / `LogusApi:Password` — без них не работает поиск брони
3. Убедитесь, что камера видна в диспетчере устройств и работает. При
   `Regula:CaptureSource=camera` (по умолчанию) `AgentScanPath` заполнять **не нужно**
4. Заполните `AlfaBankQr:Login` / `AlfaBankQr:Password` (при `TestMode=true` — тестовые
   креды банка) и выставьте `LogusApi:PaymentTransactionCode` из справочника Logus
5. Заполните `Telegram:BotToken` / `Telegram:ChatId` либо выставьте `Enabled=false`
6. Проверьте доступность VisionLine: `curl http://192.168.4.55:27015/health`
   (путь настраивается через `VisionLine:HealthPath`)
7. Убедитесь, что Logus доступен по указанному `BaseUrl`

Пункты 2–5 — не формальность: незаполненный ключ означает, что флоу гостя оборвётся
на этом шаге. Приложение проверяет конфигурацию при старте и показывает список
незаполненных ключей (см. «Проверка конфигурации при старте»).

## Архитектура

```
kiosk.html (JS)
    ↕ WebView2 bridge (JSON)
KioskActionAdapter (C#)
    ├── IPmsProvider        — PMS: Logus, Shelter, 1С:Отель, любая с REST/JSON
    │     ├── LogusApiService   (Provider=logus, боевой контракт)
    │     └── GenericPmsService (Provider=generic, конфигурируется в Pms:Generic)
    ├── IRegulaService       — распознавание паспорта (камера или считыватель)
    ├── ILogusService        — поиск брони / бизнес-заселение / отмена
    ├── IVisionLineService   — запись ключ-карт (REST, 192.168.4.55:27015)
    ├── IAlfaBankService     — оплата/возврат (СБП QR)
    ├── ICardTerminalService — оплата картой через локальный агент пинпада
    ├── INotificationService — уведомления стойке (Telegram)
    └── ICheckInSessionStore — чекпоинт сессии на диске

PaymentPollingPolicy — единый источник таймингов оплаты для C# и для kiosk.html.
PaymentCompensationService — возврат денег при сорванном заселении.
CaptureSource — камера или считыватель (разбирается один раз при старте).

Единственный путь заселения — `KioskActionAdapter` (протокол MONE). Раньше их было
три: `KioskBridgeHandler` (899 строк, «старый» протокол) и `CheckInStateMachine`
(578 строк, сага для headless). Оба были зарегистрированы в DI, но **никогда не
резолвились** — интерфейс ходит только через адаптер.

Проблема была не в размере, а в расхождении: две реализации одного флоу принимали
решения об оплате по разным правилам и уже разошлись по пяти пунктам (обработка
`null` от энкодера, `orderId` при отмене, запись чекпоинта, сброс состояния сессии).
Это стоило реальных багов — например, шлагбаум оплаты в адаптере отсутствовал
полностью, и заезд без оплаты проходил, пока его не закрыли вручную. Правя деньги
в одном пути, легко забыть про второй — и обнаружить это только на киоске.

Оба класса удалены вместе с 87 тестами (2026-10). Покрытие денежных сценариев не
потеряно: все они продублированы в тестах `KioskActionAdapter` и
`PaymentCheckpointRegressionTests`. Осталась одна реализация — править её безопасно.

Секция `CheckInStateMachine` в `appsettings.json` сохранена: её читает живой
`PaymentPollingPolicy` как источник запасных таймингов оплаты.

Logus WebAPI SelfCheckin/CheckIn — только бизнес-заселение (ключи НЕ пишет:
модули записи Keylock.* живут в Logus Desktop на стойке регистрации).
Ключ-карта пишется киоском напрямую: VisionLine REST → Энкодер ключ-карт.
```

> Оговорка про Logus: замечание выше относится к боевому адаптеру Logus.
> Для универсального PMS конкретные эндпоинты задаёт конфиг, и то, что
> PMS умеет писать ключи сама, киоском не используется.

## Деньги: что происходит при сбое

Самая опасная ситуация в киоске — гость заплатил, а заселение не завершилось.
Разбор такой сессии ведётся по чекпоинту, который пишется **до** каждой мутации
во внешних системах.

| Что произошло | Деньги | Кто разбирает |
|---|---|---|
| Гость нажал отмену до оплаты | Не списаны, QR-заказ отменён у банка | — |
| Гость нажал отмену **после** оплаты | **Возврат выполняется автоматически** | Персонал закрывает бронь |
| Статус платежа неизвестен | Ничего не делается | Персонал: стойка уведомлена |
| Logus не заселил | Чекпоинт помечен `Failed` | Персонал |
| Карта не записалась | **Возврат НЕ делается** — гость уже заселён | Персонал выдаёт карту вручную |
| Процесс упал/выключили ПК | Чекпоинт помечен `PendingManualReview` | Персонал при следующем запуске |
| Гость ушёл, не оплатив QR | Заказ истечёт сам, **возврат не требуется** | — |

### «Заказ создан» ≠ «деньги списаны»

Чекпоинт различает эти состояния, и это меняет поведение персонала:

| | `PaymentTransactionId` | `PaymentConfirmed` | `RequiresCompensation` |
|---|---|---|---|
| Гость смотрит на QR, не оплатил | задан | `false` | `false` |
| Оплата подтверждена, заселение не завершено | задан | `true` | `true` |

Раньше флаг ставился сразу после создания QR-заказа. Гость уходил, не заплатив, —
чекпоинт помечался «оплата подтверждена, сумма 5000, требуется возврат», и персонал
искал бы деньги, которых никто не платил.

Подтверждение выставляется только из ответа владельца заказа: RRN в синхронном
ответе, успешный фоновый опрос статуса или проверка на шлагбауме записи ключа.
Чекпоинт перезаписывается **после** шлагбаумов, иначе в диск ушла бы запись
с невыставленным подтверждением.

Три правила, которые за этим стоят:

1. **Возвращаем только подтверждённую оплату.** Неоплаченный QR-заказ отменяется,
   а не «возвращается» — денег ещё нет.
2. **Не возвращаем при неизвестном статусе.** Если статус платежа получить не
   удалось, автоматический возврат не выполняется: ошибка в любую сторону ударит
   по гостю или по отелю. Персонал получает уведомление с номером транзакции,
   а чекпоинт остаётся на диске.
3. **Не возвращаем дважды.** Повторная попытка отмены или ретрай не спишут деньги
   повторно (`PaymentCompensationService.AlreadyRefunded`).

При сбое записи карты возврат намеренно не делается: бронь уже в статуме проживания,
и деньги на счёте гостя — отмена оплаты противоречила бы факту.

Компенсацию делает `PaymentCompensationService` — единственный сервис на это,
вызываемый из одной точки. Так было не всегда: у адаптера возврат появился
раньше, а во втором пути `cancelReservation` тихо отменял неоплаченный заказ, и гость
оставался с деньгами за отменённую бронь. Два пути обслуживания убраны — см.
«Архитектура».

**Изоляция фонового опласа.** Опрос статуса живёт дольше запроса, который его
запустил, и метод оплаты передаётся ему параметром, а не берётся из поля сессии.
Иначе гость, не дождавшись первого QR и переключившись на карту, получил бы опрос
«qr → терминал»: фон спрашивал бы статус карточной операции у банка, а по таймауту
отменил бы QR-заказ, который уже неактуален.

`system.preflight` / `recovery.inspect` различают состояния `refund_required`
(оплачено, заселение не завершено — нужен возврат) и `conflict` (обычная
незавершённая сессия).

### Шлагбаумы перед заселением

Перед заселением в PMS проверяется:

| Проверка | Код при нарушении |
|---|---|
| Бронь найдена | `BOOKING_NOT_FOUND` |
| Оплата подтверждена у банка/пинпада (если сумма > 0) | `PAYMENT_NOT_CONFIRMED` |
| Сумма, подтверждённая банком/пинпадом, совпадает с ценой брони | `PAYMENT_AMOUNT_MISMATCH` |
| Гость уже заселён (для записи ключа) | `PMS_CHECKIN_UNKNOWN` |

Статус оплаты спрашивается у **владельца заказа** — банка или терминала, а не берётся
из ответа `payment.create` и не из состояния экрана. Единственный источник истины о
деньгах — их ответ.

Сумма сверяется отдельно от флага оплаты: если владелец заказа назвал сумму, она
сравнивается с ценой брони (принимаются и рубли, и копейки — шлюзы отдают
по-разному). Расхождение закрывает шлагбаум и уведомляет персонал, потому что
заселение по цене брони при другом списании — это либо потеря денег отеля, либо
лишняя сумма с гостя. Если сумму узнать нельзя, сверка пропускается: отсутствие
поля не повод блокировать заселение.

Повторный `payment.create` в той же сессии не создаёт второй заказ. Адаптер
спрашивает статус уже созданного: оплачен — возвращает `alreadyPaid`, не оплачен —
тот же QR, истёк — регистрирует новый. Двойной клик и ретрай UI не приводят к
двойному списанию.

Та же проверка продублирована в интерфейсе: `engine.paymentConfirmed` выставляется
только на подтверждённой оплате, и переход на шаг ключей без него блокируется. Раньше
`navigate('keys')` вызывал `registerCheckIn()` безусловно, то есть обход оплаты в UI
был открыт, и шлагбаум срабатывал уже на бэкенде. Флаг сбрасывается в `newSession` —
новый гость начинает без оплаты предыдущего.

Бесплатное проживание (комплимент, трансфер) оплату не требует: при `_price <= 0`
проверка пропускается на бэкенде. В интерфейсе бесплатная бронь помечается
подтверждённой сразу после бронирования — иначе шаг ключей был бы недостижим.

Раньше проверка оплаты была только в мосте, а в адаптере (единственном реально
работающем пути) её не было вовсе: `pms.checkin` уходил в PMS без проверки, то есть
заезд без оплаты проходил. Также `card.write` не требовал завершённого заселения —
ключ мог быть записан в бронь, которую PMS не проводила.

`PAYMENT_NOT_CONFIRMED` в UI помечен как небезопасный: повтор бессмысленен (деньги
от него не появятся), гость получает «обратитесь к администратору», а не «повторите».

## Граница доверия WebView

Мост между JS и C# даёт доступ к PMS, платежам и записи ключей, поэтому окно замкнуто
на `kiosk.html`:

- `NavigationStarting` — навигация на любой другой адрес отменяется с записью в лог, окно
  возвращается к интерфейсу. Раньше страница могла уйти на внешний URL (например, через
  `window.location`), и тот адрес получил бы право звать мост.
- `NewWindowRequested` — внешние окна запрещены: ресурс не должен открываться поверх
  экрана гостя.
- `WebMessageReceived` дополнительно сверяет `e.Source`: сообщение из iframe или из
  документа, открытого до срабатывания первой проверки, отбрасывается.

Разрешено ровно два: сам `kiosk.html` (с `?demo=1` или без) и файлы в `wwwroot/assets`
с именем-хэшем `12hex.ext` — те самые картинки, что вынесены из разметки.

Сравнение идёт по локальному пути, а не по строке URI: `file:///C:/kiosk/wwwroot` и
`C:\kiosk\wwwroot` — один путь, но разные строки. Наивная проверка «начинается с папки
приложения» пропускала бы и `appsettings.json`, лежащий рядом.

## Живость интеграций и TTL

Фронтенд считает устройство недоступным, если не получал свежих данных дольше
`CONFIG.healthTtl` (15 с) после чего отказывает в любом действии. Обновлять эти данные
должен хост: `MainWindow` каждые 10 с пингует PMS, Regula и VisionLine и отправляет
`KioskBridge.setDeviceStatus` в страницу.

Интервал опроса меньше TTL вдвое: одна просрочка не должна погасить киоск. Все пинги
идут параллельно и ограничены 12 с — зависшая интеграция не должна блокировать цикл,
иначе страница погаснет по таймауту.

Раньше единственным источником обновления был разовый `system.preflight`, а `sweepHealth`
каждые 5 с помечал всё офлайн. В боевом режиме киоск переставал работать через ~20 с
после старта; демо это скрывал строкой `if(DEMO) return true`. Энкодер отчитывается тем же
статусом, что и VisionLine — отдельного пинга у него нет.

## Границы сессии

Мост — синглтон, и его поля живут между гостями. Поэтому:

- сессия **закрывается** после успешного `writeKeys` и после завершённой отмены:
  оплата, паспорт, бронь и флаги PMS обнуляются;
- сессия **не закрывается**, если статус платежа неизвестен — персонал обязан проверить;
- поиск новой брони обнуляет состояние предыдущего гостя, поэтому брошенная
  сессия не достанется следующему гостю;
- неудачный поиск (опечатка в коде брони) сессию **не** трогает — гость повторит ввод;
- `writeKeys` без найденной брони отказывает **до** обращения к VisionLine, иначе
  энкодер успел бы записать карту в пустоту.

## Персональные данные на диске

Чекпоинт содержит номер паспорта, ФИО и дату рождения гостя, поэтому его
расположение и удаление — не вопрос вкуса.

- **Путь:** `%LocalAppData%\HotelKiosk\session.json` — приватная папка учётной
  записи, под которой запущен киоск. Раньше файл лежал в `ProgramData`, общей
  папке, доступной на чтение **любому** пользователю Windows: паспорт гостя
  читался любым процессом на киоск-ПК.
- **Хранение — двухступенчатое**, потому что чекпоинт одновременно и персональные
  данные, и единственный след оплаты, за которую гость не получил заселение:

  | Когда | Что происходит |
  |---|---|
  | сессия активна | файл обновляется на каждом шаге, ничего не трогаем |
  | через 1 час без обновлений | **ПДн стираются** (паспорт, ФИО, дата рождения), след для возврата остаётся |
  | ещё через сутки | след удаляется |

  Что хранится после обезличивания: номер брони, номер транзакции, сумма, признак
  «требуется компенсация» и шаг, на котором остановились. Гостя в этих данных
  уже нет.

  Раньше файл стирался целиком через час и молча — персонал не узнавал, что гостю
  нужно вернуть деньги, а след исчезал вместе с паспортом. При обезличивании
  бронь с компенсацией пишется в лог отдельным Warning с номером транзакции.
- **Миграция:** чекпоинт из прежнего расположения читается один раз (чтобы не
  потерять незавершённую оплату) и удаляется.
- **Фото с камеры на диск не попадает** — кадр живёт в памяти вкладки и уходит
  прямо в Regula.

## Один экземпляр киоска

Приложение берёт именованный мьютекс `Local\HotelKiosk.UI` при старте. Второй
экземпляр (двойной клик по ярлыку, автозапуск поверх работающего) молча выходит,
поднимая окно уже открытого киоска. Модального диалога здесь намеренно нет: на
киоске его некому закрыть, и висящий процесс держал бы второй экран гостя и
второй чекпоинт сессии.

### Удалённые классы

`KioskBridgeHandler` и `CheckInStateMachine` больше не существуют. В их пользу
работает `KioskActionAdapter` (протокол MONE) — единственный путь заселения.
Подробности и причины — в разделе «Архитектура».
